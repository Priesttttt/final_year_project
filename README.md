# DIMF — a runnable four-layer prototype

**Synthetic data only. Research prototype for a B.Tech viva. Not production software.**

This repository is a small, end-to-end implementation of the four-layer DIMF
framework described in the accompanying paper:

| Layer | Paper concern | What this repository actually implements |
|---|---|---|
| **L1 — Placement** | where data and documents live | small records go into an authenticated log; larger documents go to a content-addressed off-chain blob store (SHA-256), with only `sha256 + size` in the record |
| **L2 — Synchronisation** | match the mechanism to the data class | class **A** → CRDT (no write coordination); class **B** → Raft (crash-fault consensus); class **C** → PBFT (Byzantine consensus, n = 3f+1) |
| **L3 — Verifiability** | prove what was recorded | RFC 6962 Merkle tree, inclusion + consistency proofs, Ed25519-signed tree heads, roots anchored to a ledger every *b* records, standalone verifier and a browser verifier using Web Crypto |
| **L4 — Identity, policy, evaluation** | who may write what, and how well it works | Ed25519 agency identities, signed submissions, a server-enforced policy table, rejection/violation logging, and one metrics plane |

The point of the prototype is to make the paper's claims **runnable and
falsifiable**: every benchmark number in `docs/RESULTS.md` is generated by the
scripts here, and every limitation is written down rather than hidden.

## Quick start

Requirements: Python 3.11+ (the delivered environment used 3.14.10), make,
and a POSIX shell. No node, npm, CDN or internet connection is needed for the
demo.

```bash
make install          # create .venv and install pinned dependencies
make test             # deterministic pytest suite (~5 s here)
make demo             # seeds synthetic records, serves the dashboard
# open http://127.0.0.1:8000/
```

`make demo` prints the URL, the data directory and the demo anchor batch. Press
`Ctrl+C` to stop. The dashboard is a single static HTML file served by FastAPI;
it talks to the same JSON API as every other client.

Benchmarks:

```bash
make bench -- --quick   # fast run, 13 s on the development machine, < 2 min budget
make bench              # full run, still well under the 10 min budget
```

Raw CSVs and charts are written under `results/`; the tables and honest
commentary are regenerated into `docs/RESULTS.md`.

## What you can demonstrate in five minutes

1. Submit class **A**, **B** and **C** synthetic records and watch them take
   different L2 paths (0 coordination messages, Raft majority, PBFT 24 messages
   at n=4).
2. Fetch a proof for one record and verify it **in the browser** with
   `crypto.subtle.digest` — the server is not trusted for the verdict.
3. Press **Tamper** on a stored record: inclusion verification turns red even
   though the Merkle tree and signed head are untouched, and the recomputed root
   no longer matches the signed root.
4. Kill the Raft leader, watch a new leader get elected and a class-B write
   succeed, then recover the old node and watch it catch up.
5. Toggle one Byzantine PBFT backup: commits continue because n=4 tolerates
   f=1. The UI is explicit that there is **no view change**.
6. Show the anchor table: with b=10, only every tenth tree root becomes a
   ledger transaction; the rest are pending until the batch closes.

A timed viva script with what to say is in `docs/DEMO_SCRIPT.md`.

## Measured results (full run)

These numbers are copied from one real `make bench` run on the development
machine (Python 3.14.10, 16 CPUs, Linux x86-64). They vary by run and machine;
`docs/RESULTS.md` is regenerated on every benchmark run and is the
authoritative record. `make bench -- --quick` runs a smaller version in about
13 s.

| Measurement | Observed |
|---|---|
| E1 end-to-end, sequential synthetic submissions (n=600) | **166.0 records/s**, p50 **5.1 ms**, p95 **9.9 ms** |
| E1 latency by class (p95) | A **5.5 ms**, B **8.8 ms**, C **10.8 ms** |
| E2 Raft messages per entry, n=3 / 5 / 7 | **4 / 8 / 12** (exactly 2(n−1)) |
| E2 PBFT messages per entry, n=4 / 7 | **24 / 84** (exactly 2n(n−1)) |
| E2 CRDT write-coordination messages for 100 writes | **0** (one gossip round = 6 messages at n=3) |
| E3 Raft failover, n=3, 15 trials | new leader p50 **178.1 ms**, p95 **368.6 ms** (one outlier); recovered follower catch-up p50 **32.0 ms** |
| E4 PBFT, one silent backup | commits continue; **18** messages/request at n=4 instead of 24 |
| E5 Merkle inclusion proof at **m = 1,000,000** | worst case **20 hashes = 640 bytes** (index 0); shallowest leaf 12 hashes = 384 bytes |
| E5 Merkle build at 10^6 leaves | **1.20 s**; proof verification **9.5 ms** |
| E6 anchoring, n=400, simulated ledger 2 ms/tx | b=1: 400 tx, audit p50 8.4 ms; b=10: 40 tx, 22.3 ms; b=100: 4 tx, 153.7 ms |
| E6 tamper detection | **20/20** modified stored records rejected; recomputed root ≠ signed root |

**Honesty note on proof size.** RFC 6962 does not pad the tree to a power of
two, so the audit path length depends on the leaf position. The paper's
`ceil(log2 m)` figure is the **worst case**; the benchmark reports both the
worst case (index 0) and the shallowest leaf. At m=10^6 the worst case is
exactly 20 hashes (640 B), which matches the paper's bound.

## Architecture at a glance

```
 client / dashboard
   │  signed Submission (Ed25519)
   ▼
 FastAPI  ─────────────────────────────────────────────────────────────┐
   │  L4: identity registry + policy check (+ violation log)          │
   ▼                                                                   │
 L1 PlacementService                                                   │
   ├── BlobStore.put(document) -> sha256, size  (only ref goes on log) │
   └── Record (canonical JSON)                                         │
   ▼                                                                   │
 L2 SyncRouter                                                         │
   ├── A: CRDTCluster  (local write, later gossip; no coordination)   │
   ├── B: RaftCluster  (leader append, majority commit)                │
   └── C: PBFTCluster  (n=3f+1, PRE-PREPARE/PREPARE/COMMIT)            │
   ▼                                                                   │
 L3 AuthLog (SQLite)                                                   │
   ├── RFC 6962 Merkle tree over canonical record JSON                 │
   ├── Ed25519-signed tree head for every append                       │
   ├── every b records: anchor signed root to Ledger                    │
   └── inclusion / consistency proofs, tamper detection                │
   ▼                                                                   │
 Ledger (default: hash-chained SQLite; optional: EVM contract)        │
                                                                       │
 L4 evaluation plane: metrics snapshot exposed at GET /metrics ───────┘
```

All nodes are asyncio objects in **one process**, connected by a
`SimulatedNetwork` with configurable latency, jitter, drop rate, partitions,
crashes and Byzantine flags. This makes failure scenarios reproducible and the
test suite fast. It is also the main limitation: there are no real sockets,
TLS, independent failure domains or real time.

## API

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/` | static dashboard (no CDN) |
| `GET` | `/health` | liveness plus current tree size |
| `POST` | `/records` | submit a **signed** agency record; signature and policy are enforced |
| `GET` | `/log/head` | latest signed tree head |
| `GET` | `/log/stats` | tree size, root, anchors, pending, ledger backend |
| `GET` | `/log/proof/{record_id}` | inclusion proof + records + server-side check |
| `GET` | `/log/consistency?old=&new=` | RFC 6962 consistency proof + verdict |
| `POST` | `/verify` | standalone verification of a supplied proof |
| `GET` | `/ledger/anchors` | anchor history, ledger entries and stats |
| `GET` | `/cluster/status` | CRDT/Raft/PBFT node state and leader/primary |
| `POST` | `/cluster/fault` | `crash`, `recover`, `partition`, `heal`, `byzantine` |
| `GET` | `/metrics` | L4 metrics: counters, latency percentiles, messages, proof, audit delay, policy violations |
| `GET` | `/demo/agencies`, `/demo/records` | synthetic demo helpers |
| `POST` | `/demo/submit` | **demo only**: server signs for a synthetic agency |
| `POST` | `/demo/sign` | **demo only**: return a signed submission for `/records` |
| `POST` | `/demo/tamper/{record_id}` | **demo only**: corrupt stored content to show detection |

`POST /records` requires a real Ed25519 signature over the canonical submission
payload. The dashboard uses `/demo/submit` because, in a demo, the server holds
deterministic keys for the three synthetic agencies; `docs/DECISIONS.md`
explains this honestly.

Record shape hashed into the log:

```json
{
  "record_id": "SYN-00001",
  "agency": "agency-1",
  "data_class": "A",
  "timestamp": 1700000000000,
  "payload": {"amount_paise": 250000, "synthetic": true},
  "document": {"sha256": "…64 hex…", "size": 1234}
}
```

`document` is omitted when there is no attachment. Only the hash and size are
signed into the log; bytes live in the blob store.

## Real, simulated, and out of scope

| Real in this repository | Simulated / modelled | Out of scope |
|---|---|---|
| Ed25519 key generation, signing, verification (`cryptography`) | network latency, jitter, drops, partitions | production authentication/authorisation server |
| SHA-256 leaf/node hashing, RFC 6962 proof algorithms | three consensus clusters as asyncio objects in one process | real cross-machine deployment, TLS, firewalls |
| SQLite persistence of records, heads, anchors, identities, policy | ledger default (`SimulatedLedger` is a local hash chain) | public-chain deployment; EVM backend is optional and unverified here |
| policy enforcement and violation logging | synthetic agencies/beneficiaries/amounts | real government data or eligibility rules |
| Raft election, replication, crash/recover, catch-up | crash is `network.crash(name)`; process stays alive | disk-persistent Raft state, snapshots/log compaction |
| PBFT normal case with f silent/equivocating backups | message delivery is in-process | PBFT view change, Byzantine primary tolerance |
| metrics and benchmark CSVs from actual runs | benchmark workload generated from a seed | production capacity planning |

See `docs/RESULTS.md` for the generated numbers and `docs/CHALLENGES.md` for
the problems that were actually hit while building this.

## Configuration

Copy `.env.example` or export `DIMF_*` variables. The important ones:

| Variable | Default | Meaning |
|---|---|---|
| `DIMF_DATA_DIR` | `data` | SQLite DB, blobs and ledger |
| `DIMF_CRDT_NODES` | `3` | CRDT replicas |
| `DIMF_RAFT_NODES` | `3` | Raft nodes |
| `DIMF_PBFT_NODES` | `4` | PBFT nodes; must be 3f+1 |
| `DIMF_NET_LATENCY_MS` | `1.0` | simulated one-hop latency |
| `DIMF_NET_JITTER_MS` | `0.5` | simulated jitter |
| `DIMF_NET_DROP_RATE` | `0.0` | simulated drop probability |
| `DIMF_ANCHOR_BATCH` | `100` | anchor one root every b records |
| `DIMF_LEDGER_BACKEND` | `simulated` | `simulated` or `evm` |
| `DIMF_LEDGER_LATENCY_MS` | `0.0` | per-transaction ledger latency model |
| `DIMF_SEED_ON_START` | `0` | seed synthetic records on an empty DB |
| `DIMF_ALLOW_TAMPER` | `1` | enable the demo tamper endpoint |

## Tests

```bash
make test
```

The suite covers:

- RFC 6962 roots, inclusion paths and consistency paths, including the worked
  7-leaf RFC 9162 vectors and sizes 1, 2, 3, 7, 8, 9 and 1000;
- randomized Merkle properties and rejection of corrupted leaves/roots/proofs;
- Ed25519 round-trips, tampered payloads, malformed signatures;
- policy allow/deny and violation logging;
- CRDT merge laws and partition convergence;
- Raft election, replication, leader crash/failover, follower catch-up, log
  agreement, and the exact 2(n−1) message count;
- PBFT normal case, one silent and one equivocating Byzantine backup, the
  n=4/f=1 limit, and exact normal-case message counts;
- anchoring cadence `ceil(n/b)`, audit delay, persistence, tamper detection;
- full API end-to-end: auth, policy, A/B/C submission, proof, standalone
  verify, consistency, Raft failover, PBFT Byzantine toggle, tamper, metrics.

Tests are deterministic (fixed seeds/network parameters) and run in about
5 seconds in the delivered environment.

## Limitations in one paragraph

This is a **single-process, simulated-network, synthetic-data prototype**. It
does not prove production scalability, security or availability. Raft state is
in memory (the authenticated log is durable; the consensus state is not), PBFT
has no view change so a Byzantine primary is fatal, CRDT records are eventually
consistent rather than totally ordered, the default ledger is a local SQLite
hash chain rather than a public blockchain, the EVM path was not exercised in
the delivery environment, and the demo holds agency private keys on the server.
The measured numbers are real for *this* program on *this* machine, and nothing
more.
